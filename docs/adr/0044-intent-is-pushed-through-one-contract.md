# Intent is pushed through one contract, not parsed from each tool's files

AI tool activity is the widest source Observing has. Over 8–21 September 2026 on the author's machine, Claude Code sessions covered 13 of 14 days, Codex 10 of 14, and the two together all 14, across roughly seventeen client projects this machine has no repository list for; opencode's share of the same fortnight is not counted here, and the week behind `docs/intent-contract.md` now includes it. Commits in this repository covered 8, two of which were only a release. So the source is worth having, and the question is how it reaches the app. The app does not go and read it. Each tool's own configuration pushes it, through one contract: the tool's name, a line of text, an instant, an optional working directory, the tool's own session and turn identifiers, and a client, meaning what started the session or a subagent, as far as the tool says. None of them says whether a person typed the line, so the contract carries no interactive flag. Claude Code and Codex both send it from their own `UserPromptSubmit` hook, and opencode sends it from its prompt-admission hook, which fires at the same moment. Each tool's snippet is whatever its own configuration calls for: a hook line in a settings file or a `config.toml`, and a plugin file for opencode, which has no command hook. Any other tool, a `post-commit` hook, a CI step or a shell alias needs one line of the user's own configuration. The alternative was to read `~/.claude/projects/*.jsonl`, `~/.codex/sessions/**` and their equivalents. That works today, but the files are undocumented and unversioned, and two of the three tools checked, Codex and opencode, have already migrated them once: Codex keeps sessions in five overlapping places beside a `rollout-migrations/` directory, and opencode keeps a `storage/migration/` directory. An adapter per tool would be a treadmill with no end. With a contract there is no adapter to break when a format drifts, because the app parses no tool's format, and what a turn was about is decided by the snippet, which the user owns. The contract takes a path and never a Project name. A snippet knows its working directory but not the journal's Projects, and a hardcoded name in a configuration file is out of reach of any rename or merge. Project identity belongs in Project Mappings (#262), which a rename rewrites along with Notes. The unit the tools offer is a prompt, not a session. `SessionEnd` in Claude Code carries a transcript path and no prompt text, so getting anything from it means opening the transcript, which is the parsing this decision refuses. Codex's `notify` fires after the answer (`agent-turn-complete`), allows only one program, and is marked legacy in Codex's own source. Its `UserPromptSubmit` fires at the same moment as Claude Code's and carries the same fields. So an entry is one prompt, which is already the user's own prose about their work (ADR 0043). How many Notes those entries may become is not decided here. On 13 September this machine recorded 137 Claude Code sessions across fourteen project directories, against a journal averaging 2.5 Notes a day. Those sessions held about 670 typed prompts: 55 sessions had two or fewer and 24 had eight or more. (An earlier count said 131 of 137 had eight or more user turns, which counted tool results as turns.) One Note per entry, or per session, would bury the Digest, and whether a threshold on prompts per session helps is still open. Before any app code, the snippets therefore append to a plain file for a week (`docs/intent-contract.md`), and #264 chooses the unit from that reading and builds the app's command then. Rejected: parsing each tool's session files, for the reasons above. Rejected: `SessionEnd`, which has no text to push. Rejected: Codex's `notify`, for the reasons above. Rejected: a Project name in the contract. Rejected: building the command and its Settings surface before the unit is measured. Rejected: making the opencode snippet portable shell, as the other two are, because opencode has no command hook to put one in; it is a plugin file importing only node built-ins, and its cost is that one snippet out of three is not shell.
