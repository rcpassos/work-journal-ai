# Tool intent is captured through one JSON Lines contract

The automatic sources planned for Observed Notes vary in how much work they cover and what their output means. The widest source found so far — AI-tool activity — reaches 14 of 14 measured days and roughly seventeen client projects for which this machine has no repository list. Its unit is undecided. Before choosing what a day of this activity should become, measure the tools' actual event volume without writing anything into the journal.

Each tool's own hook writes one event as one JSON Lines record to a plain file the user chooses. The record carries the tool, its session or thread identifier, a turn identifier when one exists, a UTC `timestamp` for when the hook runs, an optional working directory, the text string exposed by the hook, and an `interactive` value when the tool exposes that fact. A tool that does not expose interactivity records `null`. A record never carries a Project name: the hook knows a path, while Project identity belongs in the journal's mapping layer, which can be updated when a Project is renamed or merged.

Claude Code records `UserPromptSubmit`, which fires per prompt and provides the user's prompt, session ID, and working directory. It does not provide a turn ID or an interactivity field. `SessionEnd` is not suitable: it carries session metadata and a transcript path but no prompt text. Reading that transcript is the undocumented format parsing this decision avoids.

Codex records `notify`'s `agent-turn-complete` event, which fires per turn and provides the thread ID, turn ID, working directory, user input messages, and an optional client identifier. In the current Codex implementation, `input-messages` comes from the model's retained conversation input and can repeat prompts from earlier turns. The handler records only the final string in that array rather than counting earlier prompts again. An upstream report also describes hidden background title-generation turns emitting the same event and client, without an origin field. The snippet does not filter by prompt wording, which could discard a legitimate user prompt; any generated title prompts found during the week must be identified and reported separately. The client identifier is retained; `codex-tui` is recorded as interactive, while unknown or absent values remain `null`. Its timestamp is therefore the handler's observation of turn completion, not the prompt's submission instant.

The handler scripts use portable `/bin/sh` plus `jq` for correct JSON parsing and escaping. Claude's command hook is configured to run asynchronously; Codex launches `notify` without waiting. A missing dependency, malformed payload, or file error exits successfully, prints nothing, and never changes tool behavior. The output stays outside the journal database, with no migration and no Note to undo. The scripts and setup instructions are in `docs/intent-capture/`.

Parsing `~/.claude/projects/*.jsonl`, `~/.codex/sessions/**`, or similar private stores is rejected. Those formats are undocumented and unversioned, and have already moved: Codex keeps sessions in five overlapping places beside a `rollout-migrations/` directory, and opencode has a `storage/migration/` directory. Hooks let each tool publish the user-authored text and identifiers it exposes, without a parser that can silently break when those stores change.

The corrected volume evidence makes measurement necessary. On 13 September, this machine recorded 137 Claude Code sessions across fourteen project directories, containing about 670 typed prompts. Fifty-five sessions had two or fewer prompts, and 24 had eight or more. An earlier draft's claim that 131 of 137 sessions had eight or more turns counted tool results as turns. All 137 sessions came from the desktop app; some one-prompt sessions may have been started by a tool. The week of real use must establish entries per day, sessions per day, prompts per session, the interactive share, working directories, and what a day reads like before #264 chooses an app representation.
